## 1. Scope and ownership

Repository maintainers own the dependency graph, lockfile, third-party build
inputs, license review, vulnerability response, and publication controls. A
dependency-change author owns the proposed manifest and lockfile diff. The
project owner is responsible for publication credentials, protected release
approval, and the emergency path. The accepted toolchain contract in Decision-5
and the accepted release contract in Decision-6 remain authoritative for their
respective tool and release boundaries.

## 2. Update cadence and review

Security advisories are scanned on every pull request, protected-branch push,
and weekly scheduled run. Critical or high issues are triaged within one
business day and patched or mitigated immediately. Moderate production issues
are triaged within five business days and block merge until fixed or explicitly
mitigated. Low issues are recorded and resolved in the next monthly window.

Routine dependency maintenance runs monthly. Toolchain packages are reviewed
as one TypeScript/Oxlint/tsgolint/Oxfmt/Vite compatibility tuple. Type
definitions and runtime-peer fixtures are grouped separately. A security fix
may leave the monthly window, while a peer-range change gets a focused
compatibility pull request. Runtime/peer changes require the React 18.2 and
React 19 fixtures; all changes use the typecheck, build, package, and lifecycle
evidence listed in `policy.json`.

The manifest and lockfile change together and are generated by pnpm. Reviewers
must inspect the dependency path, resolved version, lockfile integrity, source,
license result, audit result, and compatibility evidence. CI installs with
`pnpm install --frozen-lockfile`; untrusted checks add `--ignore-scripts` so a
pull request cannot execute package lifecycle code merely to be inspected.

Update automation is intentionally service-neutral. A separately reviewed bot
or scheduled process may open at most three grouped proposals and may change
only `package.json` and `pnpm-lock.yaml`. It must not merge, publish, edit this
policy, or alter exception records. No automatic merge is allowed for a
dependency or supply-chain change.

## 3. Vulnerability and license handling

The workflow runs:

```sh
pnpm audit --prod --audit-level=moderate
pnpm audit --dev --audit-level=high
pnpm audit signatures
pnpm run supply-chain:check
```

Production moderate, high, and critical advisories and development high and
critical advisories fail validation. A lower-severity development advisory is
still reviewed and tracked. An exception must name the advisory (or exact
package/license), affected version, dependency path and scope, reachability or
false-positive evidence, reason, mitigation, owner, reviewer, opened date,
and expiry. It is recorded in `exceptions.json`, never hidden by deleting a
lockfile entry. Vulnerability exceptions are rechecked on every scheduled run
and closed as soon as a fixed version or effective mitigation is available.

False-positive review first confirms the advisory ID, affected version,
dependency path, and installed artifact. The reviewer then checks reachability
and fixed-version availability, records evidence and compensating controls, and
sets a short remediation deadline. A production critical/high issue cannot be
waived through a routine exception; use the documented emergency release path
and owner approval.

The allowlist covers MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC, 0BSD,
and CC0-1.0. Every other license requires an exact, expiring exception. The
current exceptions are development-only transitive `lightningcss`/platform
packages under MPL-2.0 and `lru-cache` under BlueOak-1.0.0; none is shipped in
the package artifact. A license exception is not authorization to introduce
the same license into a runtime or distributed asset without a fresh review.

## 4. Third-party build inputs

The supply-chain workflow uses only `actions/checkout` and pins it to the full
commit `11bd71901bbe5b1630ceea73d27597364c9af683` (v4.2.2). The script rejects
unrecorded or tag-only action references in all workflow files. New actions
require maintainer review of source, release provenance, permissions, and
maintenance activity, then a monthly update review or an immediate security
update. The package manager version is exact in `package.json`; npm inputs are
integrity-pinned in `pnpm-lock.yaml`; registry signatures are checked before
the workflow succeeds.

The workflow has `contents: read`, no secrets, a 15-minute timeout, and bounded
concurrency. Fork and pull-request jobs never receive publication credentials.

## 5. Publication provenance and credentials

Decision-6 governs the release identity and ordering. The eventual protected
publication job must match package set, version, tag, merge SHA, release
manifest, tarball digest, and registry state before it publishes. npm trusted
publishing/OIDC is the normal path; `id-token: write` is granted only to the
isolated publication step and the verification portion is read-only. Registry
provenance must be checked after publication. A draft release remains draft
for any mismatch, partial asset set, or unverifiable provenance.

No long-lived npm token is used in the normal path. If the provider is
unavailable, an emergency granular package-scoped token may be injected only
into the protected publish step, never printed, committed, or made available
to fork code. The project owner records the exception and rotates/revokes the
token immediately after use. Credentials are reviewed every 90 days and on
any maintainer, provider, workflow, or suspected-exposure change. Publication
retries reconcile the immutable version/tag/merge-SHA identity first and never
overwrite a tag or republish a mismatched immutable version.
