Reference device details

The browser cannot reliably distinguish a physical camera from a virtual camera; confirm the source above yourself. The camera is requested only when you start it. The run uses your default camera and releases all session tracks when it finishes or when you stop. No camera IDs or media are uploaded; JSON is saved only when you download it.

Processing latency is measured in a separate window with a small temporary timing patch added to the cropped output. No camera alignment or external marker display is needed. FPS measurement performs no pixel readback. First-frame timing starts when getUserMedia resolves, and its request-to-stream duration is reported separately so the permission prompt is excluded from the 500 ms budget. The final retention phase briefly stops and restarts capture five times.

Heap snapshots without explicit garbage collection are reported as approximate allocation measurements; retained memory remains unknown until a controlled post-GC comparison is available. Internal video DOM experiments are optional via ?dom=1.

Camera is off. No camera permission has been requested.

Run protocol

  1. Enter the commit SHA, host/device description, and Node/package-manager versions.
  2. Start the camera and grant permission.
  3. Run three warmed trials of capture-only, pass-through, and fixed crop.
  4. Run five warm crop add/update/bypass/remove cycles and five session stop/start cycles.
  5. Review the JSON, download it, and keep the physical-device evidence with TASK-1.25.

Timing tokens pair a processor input callback with its matching output preview callback. This excludes display and camera capture delay. A run with too few matched samples records latency as unknown. Presented-frame gaps describe frames missed by the browser's video-frame callback; they do not detect source frames the camera never delivered.
